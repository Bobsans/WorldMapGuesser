# План обновления World Map Guesser

Дата согласования: 23 октября 2026 года.

Статус: выполняется. Фронтенд перенесён на новый стек; сервер Go, проверка сессий и production-деплой ещё не реализованы. Чекбоксы отмечаются после выполнения и проверки соответствующей задачи.

Первый этап реализации: перенос фронтенда на Vue 3, TypeScript, Vite и Sass (SCSS), без scoped styles. Текущее состояние и проверки описаны в [инструкции фронтенда](frontend-development.md). Go, серверная проверка сессий и production-деплой остаются последующими этапами; частичный перенос фронтенда не означает завершения всего плана.

Исходники разделены на `web/src` и `server`; frontend-конфиги находятся в `web`. Соглашения об отступах, порядке SFC и алиасах описаны в [код-стайле](code-style.md).

## 1. Цель и принятые решения

Сохранить существующую игру, переписать её техническую основу, исправить ошибки и уязвимости, обеспечить удобное управление на телефоне и автоматическое обновление на Linux после успешных проверок в GitHub Actions.

| Область | Принятое решение |
| --- | --- |
| Репозиторий | `https://github.com/Bobsans/WorldMapGuesser.git`, основная ветка `main` |
| CI/CD | GitHub Actions; проверки коммитов и pull request, автоматический деплой успешного коммита из `main` |
| Сервер | Go, HTTP-сервер на стандартной библиотеке, один исполняемый файл для Linux |
| Фронтенд | Vue 3, TypeScript, Vite, Sass (SCSS); глобальные стили без `scoped`, последние стабильные совместимые версии на момент реализации |
| Статика | HTML, JS, CSS, SVG, изображения и необходимые шрифты включаются в Go-бинарник через `go:embed`; их раздаёт приложение |
| Карта | Существующий каталог стран и SVG-контуры; собственное управление перемещением и масштабом вместо `svg-pan-zoom` |
| База | SQLite; подтверждено отдельно, MySQL не используется |
| Размещение | Один установленный бинарник и файл базы рядом в папке приложения |
| Запуск | Имеющаяся инфраструктура systemd и Nginx; Nginx принимает HTTPS и проксирует запросы приложению |
| Обновление | Проверенный бинарник заменяет установленный файл, затем служба перезапускается |
| Версии на сервере | Каталоги релизов, сохранение предыдущих бинарников, автоматические бэкапы и автоматический откат не предусматриваются |
| Геймплей | Сохраняется; новые режимы, аккаунты, мультиплеер и отдельный редизайн не входят в обновление |
| Мобильная версия | Полноценная адаптация существующего интерфейса и управления картой |

Требование «без зависимостей на сервере» означает отсутствие необходимости устанавливать Python, Node.js, npm, Go toolchain, системную SQLite-библиотеку или сервер СУБД для запуска приложения. Библиотеки разработки допустимы: они фиксируются в репозитории и входят в собранный бинарник либо статические файлы.

Go и Node.js используются в разработке и CI. Сборка на production-сервере не выполняется. Docker и постоянно работающий CI runner на сервере игры не требуются.

По исходникам уже установлены следующие проблемы:

- Экран победы предусмотрен, но игровая логика не вызывает завершение с победой.
- Сервер доверяет присланным `result`, `time`, `rights` и `wrongs`; полноценной проверки игровой партии нет.
- Проверка входных данных ограничена верхней границей результата и типом двух массивов.
- Остановка таймера при завершении выполняется после ожидания отправки результата; ошибка или задержка сети влияет на завершение интерфейса.
- Построение API-адреса использует `location.href.trim('/')`; у `trim` нет аргумента для удаления заданного символа, поэтому такой код нужно заменить корректными URL.
- Lock-файл npm исключён из Git, автоматические тесты и CI отсутствуют.
- В старой истории присутствуют учётные данные Bitbucket. Их значения не переносятся в документы, workflow или новую конфигурацию.

Точная причина неработоспособности установленной версии на Linux ещё не подтверждена логами сервера. Переписывание не требует сохранять зависимость от старого Python/Bottle.

При переносе отдельно проверить тестами обработку последнего задания, быстрые повторные клики, завершение и немедленный рестарт, сетевые ошибки, конфликт перетаскивания с выбором страны и поведение на маленьком экране.

## 3. Что сохраняется в игре

- Игрок вводит ник и начинает партию.
- Порядок заданий перемешивается; используется весь существующий каталог из 256 стран и территорий.
- Игрок находит указанную страну на карте; масштабирование и перемещение карты доступны во время партии.
- Есть три жизни. Неправильный ответ расходует одну жизнь.
- Правильный ответ отмечает загаданную страну зелёным. При ошибке красным отмечается загаданная страна, а не произвольно выбранная игроком территория.
- Уже обработанные задания не возвращаются в очередь и не принимают повторный ответ.
- Можно переключать доступные задания вперёд и назад без штрафа, включая нынешнее управление стрелками клавиатуры.
- Счёт равен количеству правильных ответов; время измеряется в секундах.
- Третья ошибка завершает игру поражением. Обработка всех заданий при оставшихся жизнях завершает её победой. Поражение имеет приоритет, если третья ошибка пришлась на последнее задание.
- Сохраняются экран результата, повторный запуск, топ-10 по счёту по убыванию и времени по возрастанию, а также просмотр карты сохранённой партии.

Исправление завершения игры и мобильная адаптация входят в план. Изменение состава каталога, географических границ, правил подсчёта очков или добавление новых игровых режимов отдельной задачей этого плана не является.

## 4. Целевая архитектура

### 4.1. Приложение и размещение

Путь запроса: браузер → Nginx/HTTPS → Go-приложение на loopback-адресе → SQLite.

Пример содержимого папки приложения; конкретный абсолютный путь определяется по текущей установке:

```text
world-map-guesser/
  world-map-guesser
  db.sqlite
```

SQLite может создавать собственные служебные файлы журнала, `-wal` и `-shm`. Они являются рабочими данными СУБД и не считаются сохранёнными версиями приложения. Деплой их не удаляет.

- Адрес прослушивания и путь базы задаются параметрами окружения systemd.
- По умолчанию база ищется рядом с исполняемым файлом, независимо от текущего рабочего каталога процесса.
- Перед первым переключением явно указывается путь существующей production-базы, чтобы запуск из другой папки не создал незаметно пустой рейтинг.
- Приложение слушает loopback-интерфейс. Внешние запросы принимает Nginx.
- Служба работает без root. Права на папку учитывают создание SQLite-журналов; права deploy-пользователя ограничены обновлением игры и перезапуском её службы.
- Логи идут в stdout/stderr и journald; отдельная инфраструктура логирования не требуется.
- При SIGTERM сервер завершает активные запросы в ограниченный срок и корректно закрывает базу.
- Небольшой `/health` сообщает готовность, включая доступность БД, и идентификатор собранного коммита.

### 4.2. Самодостаточный Go-бинарник

- Использовать стандартные `net/http`, `database/sql` и `embed` там, где их достаточно.
- Для SQLite взять драйвер без CGO, исходный выбор — `modernc.org/sqlite`; подтвердить поддержку архитектуры production-сервера и приемлемый расход ресурсов.
- Production-сборку выполнять с `CGO_ENABLED=0` под выбранные `GOOS=linux` и `GOARCH`.
- В CI проверить отсутствие динамических библиотечных зависимостей и запуск в минимальном Linux-окружении без Python, Node и системной SQLite-библиотеки.
- Включать только production-файлы фронтенда и игровые ресурсы. База, секреты, локальные настройки и тестовые данные в бинарник не попадают.
- Фронтенд собирать до Go-компиляции; отсутствие готовых ресурсов должно завершать сборку ошибкой.

`go:embed` поддерживает включение файлов при компиляции, а `modernc.org/sqlite` предоставляет SQLite-драйвер без CGO. Это позволяет реализовать выбранную упаковку. Источники: [Go embed](https://pkg.go.dev/embed), [modernc.org/sqlite](https://pkg.go.dev/modernc.org/sqlite).

### 4.3. Игровые правила и серверная проверка

- Вынести клиентские правила партии в независимый TypeScript-модуль с явными состояниями начала, игры и завершения.
- Использовать детерминированный источник перемешивания для воспроизводимых тестов и проверки партии.
- Сервер создаёт сессию с идентификатором, временем начала, порядком заданий и версией правил/каталога.
- Браузер обрабатывает карту и действия локально, без ожидания HTTP-запроса после каждого клика.
- При завершении клиент отправляет последовательность ответов и необходимых переключений заданий, а не готовый доверенный счёт.
- Сервер воспроизводит последовательность по тем же правилам и сам вычисляет правильные ответы, ошибки, жизни и итоговый счёт.
- Длительность проверяется сервером по жизненному циклу сессии. Отображение времени использует монотонное измерение, а не число срабатываний `setInterval`; правило округления согласуется между UI и API.
- Завершение сессии идемпотентно: повторная отправка не создаёт вторую запись рейтинга.
- Сессии ограничены по сроку жизни; просроченные данные и ограничения частоты запросов не должны накапливаться бесконечно в памяти или БД.
- Сбой отправки результата не удерживает таймер и не блокирует экран завершения. Повторная отправка использует ту же сессию.

Проверка партии закрывает прямую подмену счёта и противоречивые результаты. Она не обещает невозможность автоматической игры: география и клиентский код публичны.

### 4.4. SQLite и сохранение данных

- Существующие ники, результаты, время и карты ответов сохраняются.
- Схема получает идентификаторы записей, необходимую связь с сессией и индексы рейтинга; запрос топ-10 сохраняет нынешнюю сортировку.
- Миграции выполняются транзакционно и отслеживают номер схемы. Повторный запуск миграции не дублирует данные.
- Обнаруженные некорректные старые записи не удаляются молча: фиксируются число и причина, сохраняется их происхождение.
- Старым результатам не приписывается задним числом проверка новой игровой сессии.
- Параметры соединений, время ожидания блокировки, режим журнала и объём кэша выбираются по тестам для одного процесса. WAL не включается автоматически без оценки необходимости.
- Сохранение результатов и закрытие приложения проверяются на настоящем временном SQLite-файле.
- Штатный деплой заменяет только бинарник; база и её служебные файлы не копируются поверх, не очищаются и не включаются в артефакт.

## 5. Фронтенд и собственное управление картой

### 5.1. Обновление Vue и сборки

- Перенести приложение на Vue 3, TypeScript и Vite.
- Заменить глобальный event bus явным состоянием и событиями компонентов/composable-модулями.
- Типизировать страны, состояние партии, ответы API и ошибки сети.
- Сохранить назначение и содержание имеющихся экранов; адаптировать компоновку к разным размерам экрана.
- Удалить Webpack, Babel и устаревшие плагины после переноса всех используемых возможностей. Все Less-стили перенести на Sass (SCSS); использовать глобальные классы без `scoped` и без CSS Modules.
- Использовать корректные API-адреса независимо от завершающего `/`, query-параметров и разрешённой конфигурации Nginx.
- Подключать необходимые ресурсы локально; внешний Google Fonts не должен быть обязательным условием отображения интерфейса.
- Для HTML применять политику кэширования, которая позволяет получить свежую сборку после деплоя; для файлов с хешем содержимого — длительное кэширование.
- Старая открытая вкладка не должна отправлять несовместимую партию как будто она относится к новой версии правил. Версия сессии проверяется, а результат ошибки понятен игроку.

### 5.2. Замена `svg-pan-zoom`

Реализовать небольшой модуль управления SVG на Pointer Events с проверяемой математикой координат.

- Перетаскивание мышью и одним пальцем.
- Масштабирование колесом относительно положения указателя.
- Масштабирование двумя пальцами относительно центра жеста.
- Ограничения минимального/максимального масштаба и смещения, позволяющие вернуть карту в видимую область.
- Начальное вписывание карты, возврат к обзору и корректная реакция на изменение размера контейнера.
- Преобразование координат экрана в SVG с учётом масштаба, размеров и текущего преобразования.
- Pointer capture для продолжения жеста за границей исходного элемента.
- Порог движения для различения выбора страны и перетаскивания; завершение drag/pinch не считается ответом.
- Корректная отмена жеста при `pointercancel`, потере захвата, смене числа пальцев и повороте телефона.
- Отсутствие конфликтов с существующими клавишами переключения заданий и вводом ника.
- Удаление обработчиков и освобождение захвата при завершении жизненного цикла компонента.
- Изменения положения карты не должны вызывать лишнюю перерисовку всего приложения на каждое движение указателя.

### 5.3. Мобильная адаптация

- Проверить ширины 320, 360, 390, 430 и 768 CSS-пикселей, а также обычный desktop; это минимальная матрица, а не ограничение поддерживаемых размеров.
- Поддержать вертикальную и горизонтальную ориентацию, safe area и изменение доступной высоты из-за панелей мобильного браузера.
- Разместить задание, жизни, время и навигацию так, чтобы они не перекрывали основную карту.
- Сделать кнопки удобными для пальца, ориентир — область нажатия от 44 CSS-пикселей.
- Обеспечить доступ к маленьким территориям масштабированием; не менять правило выбора страны случайным расширением пересекающихся областей.
- Устранить зависимость от hover и необходимость физической клавиатуры.
- Ограничивать `touch-action` областью карты: управление игрой не должно ломать прокрутку модальных окон или масштабирование остальных частей страницы.
- Проверить ввод ника с экранной клавиатурой, длинные названия стран, рейтинг, просмотр карты результата и повторный старт.
- Сохранить видимый фокус, подписи элементов управления и управление клавиатурой на desktop.

## 6. Версии зависимостей и безопасность

### 6.1. Политика обновления

- На старте реализации выбрать последние стабильные совместимые версии Go, Vue, Vite, TypeScript и используемых инструментов. Beta/RC не использовать как основной стек.
- Проверить требования новых версий Vite/Vue к Node; Node требуется только разработке и CI.
- Записать точные выбранные версии в документации окружения, `go.mod`, `go.sum`, `package.json` и npm lock-файле.
- Удалить исключение lock-файла из `.gitignore`; в CI устанавливать фронтенд через `npm ci`.
- CI использует зафиксированные версии, а не заново выбирает `latest` при каждом деплое.
- Удалить неиспользуемые зависимости вместо переноса всего старого списка.
- GitHub Actions закрепить по полным commit SHA; обновления зависимостей проводить с повторным прохождением проверок.

### 6.2. Исправления и проверки

- Отозвать ранее записанные в проект старые учётные данные. Перед публикацией полной старой истории удалить из неё секреты; не отправлять их в публичный GitHub.
- Не хранить ключ деплоя, пароли и настройки production-доступа в исходниках или артефакте.
- Проверять размеры JSON, типы и диапазоны значений, длину ника, допустимые идентификаторы стран, порядок событий, дубликаты и терминальное состояние партии.
- Использовать параметризованные SQL-запросы, ограниченные HTTP-таймауты и предсказуемые JSON-ошибки с подходящими статусами.
- Ограничить частоту создания сессий и отправки результатов, учитывая реальный клиентский адрес только от доверенного Nginx.
- Сохранять один origin для интерфейса и API; не открывать CORS произвольным сайтам. Для запросов с cookie учесть проверку происхождения и CSRF.
- Не интерпретировать ник как HTML; проверить защиту от XSS и случайной выдачи локальных файлов через статический обработчик.
- Настроить подходящие заголовки безопасности и не включать debug-эндпоинты в production.
- Проверять Go-зависимости через `govulncheck`, npm-зависимости — аудитом, репозиторий — сканированием секретов и статическим анализом.
- Исправлять найденные применимые уязвимости; не заменять исправления отключением проверок или необоснованным игнорированием предупреждений.
- Собирать и тестировать pull request без production-секретов; доступ деплоя выдавать только job для доверенного `main`.

Тесты и сканеры подтверждают проверенные свойства и выявляют известные проблемы; они не являются обещанием отсутствия любых уязвимостей.

## 7. Тесты и измерение ресурсов

| Уровень | Обязательные сценарии |
| --- | --- |
| Правила игры | Перемешивание, переходы вперёд/назад, правильный ответ, ошибка, три жизни, все задания, победа, поражение, счёт, повторный старт, запрет ответа после завершения |
| Таймер и сеть | Монотонное время, остановка до отправки результата, медленная сеть, ошибка API, повторная отправка без второго результата |
| Геоданные | 256 записей, уникальные ID, непустые названия и контуры, одинаковая версия каталога у клиента и сервера |
| Жесты карты | Преобразование координат, пределы масштаба/смещения, drag против click, pinch, отмена жестов, resize и освобождение обработчиков |
| Go API | Реальные HTTP-запросы, валидация, серверный пересчёт, срок сессии, идемпотентность, ограничения запросов, коды ошибок |
| SQLite | Настоящие временные файлы, старая схема, миграция, отсутствие потери/дублирования записей, сортировка топ-10, блокировки и перезапуск |
| Браузер | Playwright: старт, ответ, поражение, победа, рестарт, рейтинг, preview; desktop и мобильные viewport, Chromium/Firefox/WebKit |
| Упакованное приложение | Запуск окончательного Linux-бинарника из пустой рабочей папки с отдельной временной БД; HTML, встроенные ресурсы, API, готовность и SIGTERM |
| Деплой | Передача, ошибка передачи до замены, проверка хеша, замена файла, перезапуск, неуспешный запуск, последовательные и устаревшие задания CI |

Модульные тесты фронтенда выполнять через Vitest. На Go выполнять unit/integration-тесты, `go vet` и проверку гонок в отдельном подходящем окружении CI. Production-сборка при этом остаётся без CGO; тестовый toolchain для race detector не устанавливается на сервер.

Браузерная эмуляция телефона не заменяет проверки реальных жестов. Перед завершением мобильной адаптации проверить минимум Android/Chrome и iOS/Safari, если доступны устройства; отсутствие такой проверки явно отметить.

Для сервиса измерить RSS, CPU в простое, размер бинарника и статики, холодный запуск, задержки API и работу SQLite при параллельных запросах. Зафиксировать сценарий и число одновременных клиентов, затем установить проверяемый бюджет ресурсов. Не заявлять конкретный расход памяти до измерений. Отдельно следить за очисткой сессий и отсутствием роста памяти после повторяющихся партий.

## 8. GitHub Actions: от коммита до установленного файла

### 8.1. Проверки

1. На каждый push запускать применимые проверки; на pull request выполнять тот же обязательный набор. Исключить дублирующие запуски для одного изменения, если push уже покрыт workflow pull request.
2. Проверять форматирование, ESLint, TypeScript, тесты игрового модуля, тесты Go и статический анализ.
3. Выполнять аудит зависимостей и поиск секретов.
4. Собирать production-фронтенд и Linux-бинарник под архитектуру сервера.
5. Проверять сам бинарник и проходить браузерные сценарии на упакованном приложении.
6. Сохранять артефакт бинарника, его SHA-256, идентификатор коммита и отчёты тестов в GitHub Actions.

Для smoke-проверки целевой архитектуры нужен совместимый runner или явно настроенная эмуляция. Сборка ARM-бинарника сама по себе не заменяет его запуск.

### 8.2. Деплой из `main`

1. Job деплоя получает тот же артефакт, который прошёл проверки. Повторной сборки на сервере или внутри deploy-job нет.
2. Разрешить автоматическую выкладку успешного `main`; pull request и другие ветки не получают доступ к production.
3. Выполнять только один production-деплой одновременно. Не прерывать начатую замену файла из-за следующего коммита.
4. Перед изменением сервера проверять актуальность коммита: старое задание не должно установить более старый бинарник после более нового.
5. Подключаться по SSH с проверкой известного ключа сервера и ограниченным deploy-доступом.
6. Загружать бинарник во временный файл в той же папке приложения, например `world-map-guesser.upload`. Проверять контрольную сумму и устанавливать права исполнения до замены.
7. Одним переименованием заменить фиксированный `world-map-guesser`. Это обычная замена установленного файла: временный файл не становится отдельным релизом, предыдущая версия не сохраняется. Нельзя передавать данные непосредственно поверх исполняемого файла работающего процесса.
8. Перезапустить существующую службу systemd. На первом переходе с Python один раз изменить её команду запуска и параметры окружения.
9. Проверить состояние службы и коротким запросом готовность приложения и SHA установленного коммита, включая доступ через Nginx.
10. При ошибке завершить job с ошибкой и приложить доступную диагностику без секретов. Восстановление выполняется исправленным артефактом и новой заменой файла; автоматического возврата предыдущей версии нет.

Контрольная сумма проверяет целостность передачи. Проверка службы после перезапуска сообщает фактический результат выкладки и не заменяет предварительные тесты.

На сервере не создаются `releases/`, `current`-ссылки на версии, `.old`-бинарники, резервные копии приложения или автоматические копии базы. Артефакты и отчёты CI могут храниться в GitHub по обычной политике retention; это не история версий на production-сервере.

Встроенные возможности окружений и concurrency описаны в [документации GitHub Actions](https://docs.github.com/en/actions/how-tos/deploy/configure-and-manage-deployments/control-deployments).
