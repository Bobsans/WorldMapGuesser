# Разработка и сборка Go-сервера

Backend находится в `server`, самостоятельный Vue/Vite-проект — в `web`. Фронтенд использует обычный `index.html` и знает только API-пути. Шаблонов сервера, manifest-загрузчика и префикса `/static/` нет. Production-приложение раздаёт встроенную сборку от `/`, HTTP API — от `/api`.

## Окружение

Версии зафиксированы в `server/go.mod` и `server/go.sum`: Go 1.27.3 и `modernc.org/sqlite` 1.61.0. Для разработки и сборки также нужны Node.js 24 и npm. На production-машине эти инструменты не нужны.

HTTP работает на стандартной библиотеке Go; SQLite-драйвер не требует CGO. Сборка устанавливает `CGO_ENABLED=0`. Источники: [Go embed](https://pkg.go.dev/embed), [SQLite-драйвер](https://pkg.go.dev/modernc.org/sqlite), [версии Go](https://go.dev/doc/devel/release).

## Одна команда для разработки

Из корня репозитория:

```sh
go -C server run -tags dev .
```

Go при необходимости выполняет `npm ci`, запускает `npm run dev` на свободном loopback-порту и ожидает готовности Vite. После этого интерфейс и API доступны на `http://127.0.0.1:8280/`. Запросы фронтенда и WebSocket HMR проходят через Go-прокси. Открывать внутренний адрес Vite отдельно не нужно.

При остановке Go завершается дерево дочерних процессов npm/Vite. Если Vite неожиданно завершится, Go также остановится с ошибкой. Изменения фронтенда обновляются через HMR; после изменения Go-кода команду нужно перезапустить.

Dev-база по умолчанию — `server/db.sqlite`. Для изолированного запуска можно указать `-db` и `-addr`, например:

```sh
go -C server run -tags dev . -addr 127.0.0.1:8281 -db /absolute/path/test.sqlite
```

Go-тег `dev` исключает встраивание production-ресурсов, поэтому frontend-сборка перед dev-запуском не требуется. При обновлении npm-зависимостей выполняется `npm --prefix web ci`; автоматическая установка при старте нужна только для отсутствующего `node_modules`.

## Самодостаточная сборка

Из корня репозитория:

```sh
go -C server run ./cmd/build
```

Команда собирает `web` через `npm run build`, переносит только результат `web/dist` в генерируемый `server/internal/webui/dist` и компилирует Go со встроенными файлами. Фронтенд не содержит специальных шагов для Go. Отсутствующий `index.html`, ошибка npm или ошибка Go завершают сборку ошибкой. Старые файлы bundle не смешиваются с новой сборкой.

Результат по умолчанию — `bin/world-map-guesser`, на Windows — `bin/world-map-guesser.exe`. Пример Linux-сборки:

```sh
go -C server run ./cmd/build -target linux/amd64
```

Архитектура production-сервера определяется перед деплоем; `-target` принимает Go OS/architecture. `-output` задаёт другой путь результата. `bin`, обе папки `dist`, зависимости и рабочие базы исключены из Git.

Обычный `go build` не запускает npm. Поддерживаемая команда полной сборки — `go run ./cmd/build`; она обеспечивает порядок шагов. После неё отдельная Go-компиляция может использовать уже подготовленные ресурсы. На чистом checkout production-компиляция без ресурсов завершается ошибкой `go:embed`.

## Запуск и данные

На сервер переносится один исполняемый файл. База не включается в bundle и не перезаписывается сборкой или обновлением:

```text
application/
  world-map-guesser
  db.sqlite
```

При production-запуске путь базы по умолчанию вычисляется от исполняемого файла, независимо от рабочего каталога. `WMG_DB` или `-db` позволяют задать другой путь.

| Настройка | По умолчанию | Назначение |
| --- | --- | --- |
| `WMG_ADDR` / `-addr` | `127.0.0.1:8280` | Адрес HTTP-сервера |
| `WMG_DB` / `-db` | `db.sqlite` рядом с бинарником | Существующий или новый SQLite-файл |

Флаг имеет приоритет над окружением. Логи идут в stdout/stderr; отдельных файлов логов и ротации нет. systemd сохраняет вывод в journald. SIGTERM/Interrupt запускает ограниченное по времени завершение HTTP-запросов и закрытие базы.

Старая таблица `results(user, result, time, rights, wrongs)` сохраняется на месте. Транзакционная миграция добавляет индекс рейтинга и устанавливает `user_version = 1`; повторный запуск не дублирует данные. Более новая или несовместимая схема отклоняется. Некорректные старые строки не удаляются: при чтении они пропускаются с предупреждением и числом пропусков в консоли. Новый результат проходит отдельную строгую проверку.

WAL автоматически не включается. SQLite может создавать собственный временный журнал; это рабочие данные СУБД, а не копия приложения или база для бэкапа.

## API

| Метод и путь | Поведение |
| --- | --- |
| `GET /api/health` | Готовность БД и Git-ревизия сборки; изменённый checkout отмечается `-dirty` |
| `GET /api/scores` | До 10 результатов: счёт по убыванию, время по возрастанию |
| `POST /api/scores` | Сохранение результата, ответ `{ "success": true }` |

Поля результата сохранены: `user`, `result`, `time`, `rights`, `wrongs`. Массивы содержат идентификаторы стран. Проверяются обязательность полей, JSON-типы, размер запроса до 64 KiB, ник до 64 символов, диапазоны, уникальность ответов, максимум три ошибки и соответствие счёта числу правильных ответов. Ошибки имеют JSON-поле `error` и HTTP-статус 400/413/415/500; неподдерживаемые маршруты и методы — 404/405. API не попадает в обработчик статики и не кэшируется.

HTML отдаётся с перепроверкой кэша, хешированные Vite-ресурсы из `assets` — с длительным immutable-кэшем. Списки каталогов, скрытые файлы и неизвестные пути не отдаются как `index.html`.

На этом этапе сервер хранит результат с проверкой формы и согласованности данных. Он ещё не воспроизводит партию по серверной сессии и не гарантирует честность присланных ответов; сессии, серверный пересчёт, TTL, идемпотентность и ограничения частоты остаются в [плане](repository-upgrade-plan.md). Неоднозначно завершившийся POST клиент автоматически не повторяет.

## Проверки

```sh
go -C server test -tags dev ./...
go -C server vet -tags dev ./...
npm --prefix web run check
go -C server run ./cmd/build
go -C server test ./...
```

Go-тесты проверяют старую таблицу на настоящих временных SQLite-файлах, повторную миграцию, сохранение после открытия заново, конкурентные записи, JSON-ошибки, границы API, кэш и раздачу статики. `gofmt` обязателен для Go-кода.

CI дополнительно запускает race detector, собирает Linux-бинарник и выполняет `bash server/test-package.sh bin/world-map-guesser`. Проверка копирует только бинарник в отдельную папку, запускает его из другого рабочего каталога без Node/Go в `PATH`, сохраняет результат через настоящий HTTP API, перезапускает приложение, проверяет сохранность данных и запускает Playwright против встроенного фронтенда. Браузерные сценарии используют текущие API-фикстуры. После завершения в папке остаются только приложение и `db.sqlite`.
